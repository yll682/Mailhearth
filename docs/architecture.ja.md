# アーキテクチャガイド

## 全体設計とサブシステム

Mailhearth は極めてシンプルかつ高効率なモノリス（単一バイナリ）アーキテクチャを採用しています。バックエンドは Go 言語、フロントエンドは軽量でリアクティブな Preact、データベースは組み込み SQLite（pure-Go 実装の `modernc.org/sqlite` ドライバーを採用し、cgo への依存を完全に排除）で構築されています。フロントエンドの静的ビルド成果物は、Go の `embed` 機能を通じて単一の実行可能バイナリに直接パッケージ化されます。

システム設計上の責務分担は以下の通り明確に分離されています：
- **外部メールサーバー**：プロトコルレベルのネットワーク転送、メール配信、基盤フォルダー階層、および RFC 822 形式のメール本文物理ストレージに専念します。
- **Mailhearth コアシステム**：上位の管理レイヤーおよびアプリケーションレイヤーとして機能し、組織階層、メンバーとロール、認証情報の暗号化保持、リソース関連付け、非同期管理操作、メール送信ステータス、およびチーム共同作業メタデータを永続管理します。

リポジトリ内の主要コンポーネントとその責務：
- `cmd/mailhearth`：システムの起動エントリーポイント。環境設定の読み込み、マスターキーの導出と検証、データベースの初期化、IMAP コネクションプールの初期化、バックグラウンド非同期ワーカーの協調、および HTTP/SSE サーバーのバインドを担当します。
- `internal/config`、`internal/secrets`：環境変数のバリデーション。AES-256-GCM と HKDF による多階層の鍵導出、argon2id パスワードハッシュ計算、セッショントークンのライフサイクル管理。
- `internal/db`、`internal/model`：単一トランザクションで適用される組み込みスキーマ、外部キーおよびテナントスコープ制約、コア領域エンティティと永続化データモデルの定義。
- `internal/provider`：複数メールプロバイダーの共通抽象インターフェース、ならびに Purelymail、Migadu、汎用手動 IMAP/SMTP 向けの専用アダプター。
- `internal/purelymail`：Purelymail 管理 API との通信を担う低レベルクライアントおよび構造化エラーハンドリング。
- `internal/core`：コアビジネスロジック。メール接続管理、リソースの自動検出と取り込み、組織権限管理、メールボックスのライフサイクル制御、永続化された非同期操作（Operation）、メール送信パイプライン（Submission）。
- `internal/mailproto/imappool`：接続上限クォータを厳格に管理する IMAP プール、リビジョン（Revision）駆動のプロアクティブな接続破棄機能、高効率な IMAP IDLE リアルタイムリスナー。
- `internal/mailproto/mailops`、`mimeutil`、`sieve`：IMAP/SMTP プロトコル通信。MIME メール本文の安全なサニタイズ処理と添付ファイル抽出。RFC 準拠の Sieve スクリプトコンパイラーおよび ManageSieve クライアント。
- `internal/httpapi`、`internal/web`、`web/`：セッション Cookie による認証ミドルウェア、RESTful JSON API、Server-Sent Events (SSE) によるリアルタイム通信。組み込みフロントエンドアセット、Web メールクライアントおよび管理コンソール。

## 組織モデルとリソースの所属

Mailhearth のインスタンスは、独立した 1 つの組織（`Organization`）を管理します。

1. **メンバーとロール（Member & Role）**：
   - メンバーは個人プロファイル（氏名、部署）、割り当てられたロール、およびライフサイクル状態（`invited` 招待中、`active` 有効、`disabled` 無効、`departed` 退職済み）を保持します。
   - アクセス制御は、名前付き権限（例: `mailboxes.manage`、`domains.manage` など）で構成されるきめ細かなロールに基づきます。
   - **セキュリティ不変条件**：管理権限はメール本文の閲覧権限を一切付与しません。個人メールボックス（Personal Mailbox）の所有権、または共有メールボックス（Shared Mailbox）に対する明示的な権限（`full` フルアクセス、`send` 送受信、`read` 閲覧のみ）のみが、メールデータにアクセスできる唯一の認可境界です。

2. **メール接続とドメインバインディング（MailConnection & DomainBinding）**：
   - `MailConnection` は組織に属し、プロバイダー種別、接続名、管理 API トークン／アクセスキー、対象ドメインスコープ、および 3 つの主要プロトコルのデフォルト設定テンプレートを保持します。
   - `Domain` は組織の論理ドメインを表します。`DomainBinding` はドメインを特定のメール接続に関連付け、プロバイダー固有の設定およびリアルタイムの DNS 健全性（MX、SPF、DKIM、DMARC）を監視します。
   - メールボックスのアドレスの一意性スコープは、所属するメール接続の内部に厳格に限定されます。異なる接続間で同一のメールアドレスが設定されても、互いに完全に独立しており干渉しません。

3. **アドレス体系と送信アイデンティティ（Addresses & Identities）**：
   - アドレスは複数の用途に対応します：メイン（`primary`）、エイリアス（`alias`）、転送（`forward`）、グループ（`group`）、キャッチオール（`catchall`）、プレフィックス（`prefix`）、および外部管理ルール（`external_rule`）。
   - メールボックス転送ルールは独立して `mailbox_forwardings` テーブルに保存され、取り込み時にも所属するメインメールボックスの関連が自動維持されます。
   - 送信者アイデンティティ（Identity）の表示設定と SMTP 送信認可は明確に分離されています。受信エイリアスを所有している場合でも、そのアドレスを送信元（From）として送信する権限は自動付与されず、明示的な認可が必要です。
   - グループ配信リストは部署やルールに基づいて対象となるすべての個人メールボックスを動的に解決し、配信前に接続とドメインの制限を検証した上で重複送信先を正確に排除します。

4. **リモートリソースマッピング（ProviderResource）**：
   - メールプロバイダーのリモート参照（リモートメールボックス ID、エイリアス ID 等）をローカルオブジェクトおよび業務用途に一対一で関連付けます。
   - リビジョン（Revision）検証と外部キー制約により、組織や接続の境界を越えた不正な参照を防ぎ、監査履歴の改ざんを防止します。

## プロトコル設定と認証情報の分離

各メールボックス（Mailbox）は、IMAP、SMTP、ManageSieve の 3 つの独立したプロトコルエンドポイント（Endpoint）を持ちます：
- **ネットワークモード（Network Mode）**：各エンドポイントは `inherit`（メール接続の全体テンプレートを継承）、`override`（独立したホストとポートを指定）、または `disabled`（プロトコルを無効化）から設定可能です。
- **認証情報モード（Credential Mode）**：`managed`（プラットフォームが自動生成・管理する認証情報）または `entered`（手動入力されたパスワード）に対応します。有効なエンドポイントごとに暗号化された認証情報を個別に保持します。
- **原子的な有効化保証**：プロトコル設定の変更時、システムは事前に有効化されるすべてのプロトコルに対してバックグラウンドで接続認証テストを実行します。すべてのプロトコルで認証が成功した場合にのみ、単一のローカルトランザクションで変更を確定します。
- **コネクションの安全な破棄**：エンドポイント設定、認証情報、またはアクセス権のリビジョンが変更されると、IMAP コネクションプールは即座に関連する古い接続を切断し、次回のアクセス時に安全な再接続を強制します。
- **プロバイダー初期値**：
  - Purelymail：IMAP (`imap.purelymail.com:993` TLS)、SMTP (`smtp.purelymail.com:465` TLS)、ManageSieve (`mailserver.purelymail.com:4190` STARTTLS) を標準で有効化。
  - Migadu：IMAP (`imap.migadu.com:993` TLS)、SMTP (`smtp.migadu.com:465` TLS) を標準で有効化、ManageSieve は標準で無効化。
  - 手動接続：すべてのエンドポイントが初期状態で無効化されており、管理者が個別設定。
  - TLS 証明書検証：ホスト OS の信頼済み CA 証明書チェーンを使用するほか、カスタムプライベート CA 証明書バンドルの指定にも対応し、サーバーホスト名（SNI）を厳格に検証。

## リソース検出、取り込みと永続的な管理操作

1. **リソース検出と選択的インポート**：
   - 検出（Discovery）は指定された接続配下のリモート全リソースを完全に走査し、有効期限付きのスナップショットを生成して現在の接続 Revision に紐付けます。
   - インポート実行時、単一トランザクション内で所属関係、リビジョン、有効期限、依存関係を厳格に検証します。インポートされた個人メールボックスは初期状態で未割り当て（Owner なし・ローカルログイン不可）となり、後から管理者が安全に割り当てます。
   - 同期（Sync）は登録済みリソースの観測データを安全に更新し、新規リソースはインポート待機リストに保持されます。すでに割り当てられた Owner、アクセス権、社内メモ、署名、手動認証情報はそのまま維持されます。
   - 転送ルールの取り込みでは、転送元メールボックス、宛先の確認状態（`active`、`pending_confirmation`、`blocked`、`unknown`）、リモート参照が正確に保持されます。未検証の転送は `unverified` のままとなり、Migadu の転送書き込みは厳格な配信検証によって保護されます。

2. **永続非同期オペレーションエンジン（Operation Engine）**：
   - 外部プロバイダーとの通信や長時間の処理を伴う管理操作はすべて `Operation` エンティティを通じて実行され、一意の `requestId`、ペイロードダイジェスト、暗号化データ、リソース排他ロック、ステップ別進行状況を記録します。
   - **厳格な冪等性**：同一の `requestId` による再リクエストは既存の操作状態をそのまま安全に返し、多重実行を防止します。設定リビジョンが変更されたり実行権限が失効した場合は、古いタスクの実行を未然に遮断します。
   - **不確定状態の封じ込め**：外部への書き込み時にネットワークタイムアウト等で結果が不確定となった場合、タスクは確認待ち状態に移行し、完了確認済みのステップが無暗に再実行されることはありません。
   - **外部管理者レポート**：プロバイダー管理画面での手動作業が必要なステップでは、管理者の完了報告を記録し、`systemVerified=false` として安全に管理します。認証情報作成中に通信が途絶しリモート ID が不明となった場合、明示的なクリーンアップ報告を必須とします。
   - **退職・引き継ぎフロー（Offboarding）**：メールボックスの後任への引き継ぎまたはアーカイブ保持、グループ所属の解除、アクティブセッションの即時失効、外部認証情報の失効を、永続化されたステップとして確実に記録します。

## メール送受信とセキュアな描画パイプライン

1. **認可解決とコネクション割り当て**：
   - HTTP リクエスト受信時、ミドルウェアが呼び出し元の身分、セッションの有効性、対象メールボックスのアクセス権を解決し、利用可能なプロトコルエンドポイントを動的に特定します。
   - IMAP コネクションプールは 3 段階の上限を適用します：システム全体で 24、メール接続ごとに 8、メールボックスごとに 3。バックグラウンド IDLE リスナーの動作中も、全体で 4、接続ごとに 2 のスロットを対話型リクエスト用として確実に確保します。

2. **メール取得と特殊フォルダー判定**：
   - `mailops` パッケージが IMAP コマンドを実行し、フォルダー一覧取得、ページネーション、サーバーサイド検索、MIME 構造解析を高速に処理します。
   - 特殊フォルダーは「管理者の明示的マッピング > RFC 6154 `SPECIAL-USE` 属性 > 一意の標準名称／ローカライズ名称」の厳格な優先順位で確実に判定されます。

3. **コンテンツサンドボックスによる徹底防御**：
   - メールの HTML 本文はサーバー側の `mimeutil` により徹底的に無害化され、不正なスクリプト、危険な CSS、追跡ビーコンを排除します。インライン添付ファイルは安全な内部 `cid:` エンドポイントへと変換されます。
   - メール本文は、厳格な Content Security Policy (CSP) が適用されたスクリプト無効のサンドボックス `<iframe>` 内で安全に描画されます。外部画像はトラッキング防止のため初期状態でブロックされ、ユーザーの明示的な要求でのみ読み込まれます。

4. **高信頼な送信パイプライン（Submission Pipeline）**：
   - 送信リクエストはデータベースに永続化されます：一意で不変の `Message-ID`、コンテンツダイジェスト、暗号化エンベロープを記録し、本文はサーバーの Drafts（下書き）フォルダーに一時ステージングされます。
   - **ステップの完全分離**：SMTP への引き渡しと送信済みフォルダー（Sent）へのコピー保存は独立したステップとして記録されます。送信結果が不明な場合に自動再送して二重配信を引き起こすことはありません。Sent コピーの保存失敗時にはコピー保存のみを再試行し、SMTP を重複送信しません。下書きのクリーンアップは正確な UID EXPUNGE で実施されます。

5. **リアルタイムなチーム協調**：
   - 共有メールボックスは IMAP IDLE リスナーを通じて新着メールを即座に検知し、Server-Sent Events (SSE) を通じてブラウザーにリアルタイム配信します。
   - 共同作業メタデータは `mid:<message-id>` に紐付けられます。`message_state` が担当者と解決ステータスを管理し、`mail_activity` が返信、転送、担当割り当て、社内メモの履歴をフォルダー移動後も確実に保持します。

## メールルールシステムとフロントエンドアーキテクチャ

1. **Sieve フィルタリングと自動返信**：
   - 構造化されたルール設定は、メールサーバーが ManageSieve を通じて宣言した拡張機能に合わせて標準の Sieve スクリプトに動的コンパイルされます。
   - ルール適用前、サーバー上に既存の有効スクリプトがあるかハッシュ値を確認します。既存スクリプトを引き継ぐ場合は確認ダイアログを表示し、不慮のスクリプト上書きを防止します。

2. **モダンシングルページアプリケーション（SPA）**：
   - Preact と `@preact/signals` を採用してリアクティブな状態管理を実現し、軽量な History Router で `/mail`、`/admin`、`/settings`、`/login`、`/invite/:token`、`/setup` をルーティングします。
   - レスポンシブレイアウト：画面幅 860px 以上では効率的な 3 カラム表示（フォルダー、メール一覧、本文閲覧エリア）、モバイルおよびコンパクト画面では 1 カラムとドロワーナビゲーションに自動切り替え。
   - **多言語対応**：英語を原本とし、簡体字中国語（zh-CN）、繁体字中国語（zh-TW）、日本語（ja）、スペイン語（es）の 4 つの辞書を提供。テストフレームワークが TypeScript 抽象構文木（AST）を走査し、翻訳キーの網羅性とテンプレート変数の対称性を自動検証します。
