# セキュリティ

[English](security.md) · [简体中文](security.zh-CN.md) · [繁體中文](security.zh-TW.md) · **日本語** · [Español](security.es.md)

## 脅威モデル

Mailhearth はスタッフのブラウザーと Purelymail の間に位置し、アカウント上の
すべてのメールボックスを作成、削除、リセットできる API トークンを保持して
います。機密性の高い順に、保護すべき資産は次のとおりです。

1. Purelymail API トークン。
2. IMAP/SMTP/Sieve へのアクセス用に保持するメールボックスのアプリパスワード。
3. メール本文と組織のディレクトリ。
4. メンバーのセッション。

想定する攻撃者は、インターネット上の攻撃者、悪意のあるメールまたはフィッシング
メール、退職した従業員、付与されていないメールボックスを読もうとするメンバー
です。ホスト自体の侵害は影響範囲の限定を除いて対象外です（機密情報は保存時に
暗号化されるため、データベースのコピーだけでは役に立ちません）。

## 対策

**保存時の機密情報。** `secrets.Box` はインストールのマスターキーから
HKDF-SHA256 で導出した鍵を使い、AES-256-GCM で値を封緘します。マスターキーは
`MAILHEARTH_MASTER_KEY`、または初回起動時に生成される `<data>/master.key`
（モード 0600）から取得します。用途ごとに異なる導出鍵を使用します。API トークン
は保存後にマスクされたヒントとしてのみ表示され、アプリパスワードは一切表示
されません。

**認証。** メンバーのパスワードは argon2id（19 MiB、t=2）です。セッションは
ランダムな 256 ビットのトークンで、SHA-256 でハッシュ化して保存します。
Cookie は `HttpOnly`、`SameSite=Lax`、ベース URL が HTTPS の場合は `Secure` で、
有効期限は 30 日のスライド式です。ログインと招待の承諾には IP 単位のレート制限
があります。メンバーを無効化または退職処理すると、そのメンバーのセッションは
すべて直ちに失効します。

**認可。** すべての管理エンドポイントはメンバーのロールの権限を確認します。
オーナー専用の操作（譲渡）には `org.owner` が必要です。メールのエンドポイントは
`core.ResolveMailbox` でメールボックスを解決し、所有権または明示的なアクセス
許可を要求し、許可レベルを強制します（`read` はフラグ付けも送信もできず、
`send` は削除も移動もできません）。管理権限がメールへのアクセスを意味すること
は決してありません。

**CSRF。** 状態を変更する `/api` リクエストには `X-Requested-With: Mailhearth`
を付ける必要があり（ブラウザーは CORS なしではクロスオリジンでこれを追加
できません）、`Origin` ヘッダーが存在する場合はホストと一致しなければなりません。

**信頼できないメールコンテンツ。**
- HTML はサーバー側で許可リスト（bluemonday）によりサニタイズし、さらに DOM
  パスで危険な CSS（`expression`、`url()`、`position:fixed`）を除去し、`cid:`
  画像を認証済みのパート URL に書き換え、要求されない限りリモート画像を
  ブロックし、リンクに `target=_blank rel=noopener noreferrer` を強制します。
- サニタイズ済みのドキュメントは専用の URL から
  `Content-Security-Policy: default-src 'none'; img-src 'self' data:; style-src
  'unsafe-inline'; script-src 'none'; form-action 'none'` を付けて配信し、
  `<iframe sandbox="allow-same-origin allow-popups …">` 内に `allow-scripts`
  なしで表示します。`allow-same-origin` を残すのは、親ページが高さを測定
  できるようにするためだけであり、いずれにせよ CSP により内部でスクリプトを
  実行できないことが保証されています。
- iframe はメンバー、メールボックス、フォルダー、UID に紐づけられた短命の
  HMAC ビュートークンで認証されるため、Cookie は不要です。
- 添付ファイルは、安全にインライン表示できる種類（ラスター画像、PDF、
  音声・動画、text/plain）でない限り `Content-Disposition: attachment` で
  配信します。HTML、SVG、XML は決してインラインでレンダリングしません。
  `X-Content-Type-Options: nosniff` はすべての応答に付けます。
- 作成した HTML と署名は送信前に同じサニタイザーを通るため、侵害された
  ブラウザーセッションでもメールにスクリプトを挿入できません。
- メッセージと添付ファイルのサイズには上限があります
  （`MAILHEARTH_MAX_UPLOAD_MB`、`MAILHEARTH_MAX_MESSAGE_MB`）。2 MB を超える
  テキストパートは表示時に切り詰めます。

**アプリケーションのヘッダー。** `X-Frame-Options: DENY`、`Referrer-Policy:
no-referrer`、SPA 用の CSP（`script-src 'self'`）、ハッシュ付きアセットのみの
イミュータブルキャッシュ、API 応答の `no-store`。

**Purelymail の認証情報。** メールボックスごとに 1 つのアプリパスワード。
引き継ぎ、共有への変換、停止、退職処理のいずれでもこれをローテーションし、
Purelymail のパスワードもリセットするため、退職者が設定したスマートフォンや
デスクトップクライアントは動作しなくなります。古いアプリパスワードは上流で
失効させます。

**Sieve。** ルールは構造化モデルからコンパイルし、ヘッダー名、サイズ、
アドレス、フラグを検証します。ユーザーが生の Sieve を送信することはできません。

**監査。** すべての管理上の変更は、実行者、対象、詳細とともに `audit_log` に
記録されます。

## デプロイの推奨事項

- リバースプロキシで TLS を終端し、`MAILHEARTH_BASE_URL` を HTTPS のオリジン
  に設定して Cookie が `Secure` になるようにします。プロキシが
  `X-Forwarded-For` を設定する場合に限り、
  `MAILHEARTH_TRUST_PROXY=true` を設定します。
- `master.key` はデータベースとは別にバックアップし、パスワードマネージャーに
  保管します。これがない場合、保存済みの認証情報は再作成する必要があります
  （製品側で可能です。すべてのメールボックスをローテーションします）。
- Mailhearth 専用の Purelymail API トークンを使用すると、単独で失効できます。
- Purelymail アカウント自体で二要素認証を有効にします。API トークンはこれを
  回避するため、上記のとおり最も重要な資産となっています。
