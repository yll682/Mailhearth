# セキュリティ仕様と脅威対策ガイド

## 脅威モデルと保護対象資産

Mailhearth はネットワーク構成上、スタッフのブラウザーと外部メールプロバイダー（Purelymail、Migadu、または自社メールサーバー）の中間に位置します。組織管理と日々の送受信を集約するハブとして、システムが定義し保護するコア資産を機密性順に以下に示します：

1. **各メール接続の管理 API 認証情報**: ドメイン、アカウント、およびサーバー側ルーティングルールを操作できる最高権限；
2. **メールボックスのプロトコル認証情報**: IMAP、SMTP、ManageSieve での送受信およびルール管理に使用されるパスワードまたはアプリ専用パスワード；
3. **メールデータと組織アドレス帳**: チームの過去のメッセージ履歴、下書き、共有メールボックス内の社内メモ、メンバー名簿；
4. **メンバーのアクティブセッション（Sessions）**: ログイン済みメンバーのブラウザー状態と一時的な認証トークン。

### 潜在的な脅威と防御境界
Mailhearth のセキュリティ設計は、以下の主要な攻撃ベクトルに対して多層防御を実施しています：
- **インターネット上の攻撃者**: パスワードの総当たり攻撃、クロスサイトリクエストフォージェリ（CSRF）、権限昇格 API の悪用によるデータ詐取；
- **悪意ある送信者・フィッシングメール**: 特殊な HTML 本文を通じた悪意あるスクリプトの挿入（XSS）、CSS フィッシングオーバーレイ、リモート画像ビーコンによる IP アドレスや閲覧状況の追跡；
- **退職者・権限のない内部ユーザー**: 失効していないアクセス経路の悪用、自分に割り当てられていない個人メールボックスや機密性の高い共有メールボックスの不正閲覧；
- **悪意のある外部クライアント**: サードパーティメールクライアント向けアプリ専用パスワードの不正取得や盗聴。

> **境界に関する注意**: 物理サーバーの乗っ取りや OS の root 権限奪取は本ソフトウェアの防御対象外です。ただし、システムは**保存データの完全暗号化（Encryption at Rest）**によって被害範囲（Blast Radius）を最小限に抑えます。データベースファイル全体が持ち出された場合でも、安全に分離管理された `master.key` がなければ、平文の認証情報は一切復号できません。

## 主要なセキュリティ対策

### 1. 認証情報の安全な暗号化（Secrets at Rest）
- **暗号化標準**: `internal/secrets` パッケージに実装されており、業界標準の AES-256-GCM 認証付き暗号を採用しています。
- **階層型鍵導出**: サーバー側のマスターキー（環境変数 `MAILHEARTH_MASTER_KEY` または権限 `0600` で保護された `<data>/master.key`）から、HKDF-SHA256 を用いてコンテキストごとに完全に分離されたサブキーを導出します。
- **平文漏洩の防止**: 通常の管理 API クエリで平文パスワードや API トークンが返されることは決してなく、安全なマスク情報のみが表示されます。
- **ワンタイム受け取り手順（One-Time Claim Flow）**: 外部クライアント向けに新しいアプリ専用パスワードを生成する場合、権限を持つ管理者が期間限定の受け取りチャンネルを通じて明示的に 1 度だけ取得できます。レスポンスには `Cache-Control: no-store` が強制付与され、取得直後にサーバーメモリ上の平文データは完全に破棄されます。

### 2. 認証とセッションの堅牢化（Authentication & Sessions）
- **先進のパスワードハッシュ**: メンバーパスワードは RFC 9106 推奨の argon2id（`m=19MiB, t=2`）で保護され、GPU や ASIC によるオフライン総当たり攻撃に強力に対抗します。
- **高エントロピーなセッショントークン**: 256 ビットの暗号論的擬似乱数トークンを生成し、データベースには SHA-256 ハッシュのみを保存します。Cookie には `HttpOnly`、`SameSite=Lax`、および HTTPS 環境での `Secure` を強制し、30 日間のスライディング有効期限を設けています。
- **総当たり攻撃を防ぐレート制限**: ログインや招待リンク承諾などの認証エンドポイントに対し、IP アドレスおよびアカウント単位で多層のレート制限を適用します。
- **退職時の即時セッション破棄**: メンバーが無効化（`disabled`）または退職（`departed`）処理された場合、単一のローカルトランザクションで即座にすべてのアクティブセッションを無効化します。

### 3. きめ細かな認可モデルとメールボックスの分離（Authorization）
- **特権の直交分離**: ドメイン設定やメンバー管理などの管理権限と、メールの閲覧権限は完全に切り離されています。組織管理者であっても、他のメンバーの個人メールボックスを閲覧する権限は自動的には与えられません。
- **厳格な認可境界**: すべてのメール操作は `core.ResolveMailbox` を経由して動的に判定され、個人メールボックスの所有権または共有メールボックスの認可レベル（`read` 閲覧のみ・フラグ付けや送信は不可、`send` 閲覧と送信・削除や移動は不可、`full` 完全管理）が厳格に適用されます。

### 4. 厳格な全方位 CSRF 対策
- 状態を変更するすべての HTTP リクエスト（POST、PUT、PATCH、DELETE）に対し、カスタムヘッダー `X-Requested-With: Mailhearth` の付与を義務付けています。ブラウザーの同一オリジンポリシーにより、CORS で許可されていない外部サイトはこのヘッダーを送信できません。
- リクエストに `Origin` ヘッダーが含まれる場合、サーバーに設定された `MAILHEARTH_BASE_URL` と完全に一致することを検証します。

### 5. 信頼できないメール本文のサンドボックス隔離（Untrusted Content Sandboxing）
メールは外部からの信頼できないコンテンツの最大の流入経路です。Mailhearth は厳格な多段階サニタイズパイプラインを実施しています：
- **サーバー側での徹底的なホワイトリスト消毒**: メールの HTML は `bluemonday` による厳格なタグホワイトリストで処理された後、DOM の二次走査を受けます。危険な CSS 構文（`expression`、`url()`、`position: fixed` など）を除去し、`cid:` インライン画像を認証付きエンドポイントに書き換え、外部リンクには `target="_blank" rel="noopener noreferrer"` を強制します。
- **リモート画像の標準ブロック**: 外部画像はトラッキングピクセルや IP アドレスの調査を防ぐため初期状態でブロックされ、ユーザーが明示的に要求した場合にのみ読み込まれます。
- **スクリプト無効サンドボックスでの描画**: 消毒済みの HTML は専用の隔離 URL から厳格なヘッダーで配信されます：
  ```http
  Content-Security-Policy: default-src 'none'; img-src 'self' data:; style-src 'unsafe-inline'; script-src 'none'; form-action 'none'
  ```
  そして、`<iframe sandbox="allow-same-origin allow-popups ...">` 内に描画されます。ここには**`allow-scripts` が一切含まれていません**。未知のブラウザ脆弱性が存在した場合でも、スクリプトの実行は根本から遮断されます。
- **Cookie 不要の短命 HMAC 表示トークン**: iframe の読み込みは、対象メンバー、メールボックス、フォルダー、メッセージ UID に紐付けられた短命な HMAC view token で認証されるため、Cookie の送信を必要としません。
- **添付ファイルの安全な配信**: すべての添付ファイルは `Content-Disposition: attachment` および `X-Content-Type-Options: nosniff` ヘッダー付きで配信されます。画像、プレーンテキスト、PDF を除き、HTML、SVG、XML はインライン表示が厳格に禁止されています。
- **送信時と署名の対称サニタイズ**: ユーザーがエディターで作成した本文および署名も、SMTP 送信前に同一のサニタイザーを通過するため、悪意あるブラウザー拡張機能によるスクリプト混入を防ぎます。

### 6. アプリケーションセキュリティヘッダー
- クリックジャッキング防止: `X-Frame-Options: DENY`；
- リファラープライバシー保護: `Referrer-Policy: no-referrer`；
- SPA クライアント用 CSP: メイン画面は `script-src 'self'` に限定；
- API キャッシュの抑制: すべての `/api/` レスポンスに `Cache-Control: no-store` を付与。

### 7. プロトコル通信と TLS 証明書検証
- 有効化されたすべての IMAP、SMTP、ManageSieve 接続において、リモートサーバーの証明書とホスト名（SNI）を厳格に検証します。ホスト OS の信頼済み証明書ストアを使用するほか、プライベート CA 証明書バンドルの指定にも対応します。
- システムには「証明書エラーを無視する」などの危険な設定項目は一切存在しません。

### 8. 改ざん防止監査ログ（Audit Trail）
- メンバーの追加、ロール変更、接続設定、認証情報ローテーションなどの重要な管理操作は、実行者 ID、アクセス元 IP、タイムスタンプ、変更差分とともに `audit_log` テーブルへ永続的に記録されます。

## 運用セキュリティの推奨事項

1. **HTTPS の強制とリバースプロキシの適切な設定**: Caddy や Nginx などのリバースプロキシで TLS を終端し、`MAILHEARTH_BASE_URL` を `https://` で始まる URL に設定して Cookie の `Secure` 属性を有効化してください。プロキシが信頼できる場合にのみ `MAILHEARTH_TRUST_PROXY=true` を有効化してください。
2. **マスターキー（master.key）の分離保管**: `/data/master.key` をデータベースバックアップと同じ場所に保管しないでください。1Password や Bitwarden などのパスワード管理ツールや、専用の安全なストレージに保管することを推奨します。
3. **Mailhearth 専用の API トークンの利用**: Purelymail や Migadu で作成する API トークンは、Mailhearth 専用として発行し、他のサービスと共用しないでください。
4. **プロバイダー本体での二要素認証（2FA）の有効化**: メールプロバイダーの公式管理アカウントには必ず 2 要素認証を設定し、基盤インフラの乗っ取りを防止してください。
