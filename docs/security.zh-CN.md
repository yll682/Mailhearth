# 安全规范与威胁防护指南

[English](security.md) · **简体中文** · [繁體中文](security.zh-TW.md) · [日本語](security.ja.md) · [Español](security.es.md)

## 威胁模型与保护资产

Mailhearth 在网络架构上位于员工终端浏览器与上游邮件服务商（Purelymail、Migadu 或自建邮件服务器）之间。作为聚合管理与日常收发的枢纽，系统界定并保护的核心数字资产按敏感度排列如下：

1. **各邮件连接的管理 API 凭据**：具有操作远端域名、账户分配与路由规则的最高系统权限；
2. **各邮箱协议凭据**：用于 IMAP、SMTP 及 ManageSieve 实际收发信与规则配置的密码或应用专用密码；
3. **邮件数据与组织通讯录**：团队的历史邮件往来、草稿、共享邮箱协作内部备注以及成员花名册；
4. **成员的活动会话（Sessions）**：已登录成员的前端状态与临时鉴权令牌。

### 潜在威胁与防御边界
Mailhearth 的安全设计针对以下攻击面实施纵深防御：
- **公共互联网攻击者**：试图通过弱口令暴力破解、CSRF 跨站请求伪造或越权 API 窃取组织数据；
- **恶意/钓鱼邮件发件人**：试图通过特制 HTML 邮件正文注入恶意 JavaScript 脚本（XSS）、触发 CSS 钓鱼注入、或通过内嵌远程图片探测员工真实 IP 与阅读状态；
- **离职或非授权内部成员**：试图保留未授权的访问通道，或越权窥探未分配给自己的个人邮箱与敏感共享邮箱；
- **恶意外部客户端**：试图未经授权拦截或窃取第三方邮箱客户端的应用密码。

> **边界说明**：物理宿主机或操作系统完全被攻破不在软件防御边界内。但系统通过**全链路静态加密**将影响面（Blast Radius）降到最低——即便数据库文件被整体窃取，在没有独立保存的 `master.key` 的情况下，攻击者也无法解密出任何明文凭据。

## 核心安全控制措施

### 1. 静态凭据强加密（Secrets at Rest）
- **加密算法**：基于 `internal/secrets` 模块，采用业界公认的 AES-256-GCM 认证加密。
- **密钥派生体系**：服务器端的主加密密钥（来自环境变量 `MAILHEARTH_MASTER_KEY` 或自动生成的 `<data>/master.key`，权限严格限定为 `0600`）通过 HKDF-SHA256 按照业务上下文派生出完全隔离的子密钥，确保不同用途的加密互不交叉。
- **敏感数据防外泄**：常规 API 查询绝不向前端返回任何明文密码或 API 令牌，仅显示脱敏后的掩码信息。
- **一次性密码安全提取（One-Time Claim Flow）**：当系统为外部客户端生成新的应用密码时，仅允许具备权限的管理员在短暂的时效窗口内明确领取一次；响应头强制附带 `Cache-Control: no-store`，领取完成后系统立即永久销毁明文暂存，防止重放或浏览器缓存泄露。

### 2. 身份认证与会话防护（Authentication & Sessions）
- **强密码哈希**：员工登录密码采用 RFC 9106 推荐的 argon2id 密码哈希算法（参数调优为 `m=19MiB, t=2`），高抗 GPU/ASIC 离线暴力破解。
- **高强度会话令牌**：会话基于 256 位加密安全伪随机数生成，数据库仅保存其 SHA-256 哈希值；Cookie 严格附加 `HttpOnly`、`SameSite=Lax` 并默认附加 `Secure`（仅纯 HTTP 测试实例可设置 `MAILHEARTH_SECURE_COOKIES=false` 关闭），采用 14 天滑动过期窗口。滑动窗口由 `MAILHEARTH_SESSION_DAYS` 控制，并受 30 天绝对有效期（`MAILHEARTH_SESSION_MAX_DAYS`）约束；修改本人密码后，该成员的其他会话会全部注销。
- **强制初始化令牌**：在全新实例上创建组织必须提供初始化令牌，避免抢先访问新实例的人占用所有者身份。未设置 `MAILHEARTH_SETUP_TOKEN` 时，在初始化完成前每次启动都会生成一个随机令牌并输出到服务器日志；若没有可用令牌，该接口一律拒绝请求（fail closed）。
- **防暴力破解速率限制**：对用户登录、邀请链接激活等敏感认证接口实施基于 IP 与账户维度的多层速率限制。只有当请求来自 `MAILHEARTH_TRUSTED_PROXIES` 所列代理时，系统才会从 `X-Forwarded-For` 读取客户端地址。
- **离职立即吊销**：成员一旦被管理员停用（`disabled`）或标记离职（`departed`），系统在单个本地事务中立即清空并注销该成员的全部在线会话，杜绝幽灵会话残留。

### 3. 细粒度权限模型与邮件隔离（Authorization）
- **权能正交隔离**：管理控制权限（如域绑定、成员管理）与邮件阅读权限完全隔离。拥有管理员角色绝不默认拥有查阅团队其他成员个人邮箱的权力。
- **管理层级约束**：管理者只能操作权限为其自身权限子集的成员（重置密码、发送邀请、修改资料与角色、启用或停用、离职处理、删除），且只能授予自己拥有的权限；组织所有者账号只能由所有者本人管理。
- **所有权与授权边界**：邮件访问必须通过 `core.ResolveMailbox` 进行实时权限判定，严格检验个人邮箱的所有权或共享邮箱的明确授权级别（`read` 仅可查看不可加星标或发信；`send` 可读可发但不可删除或移动；`full` 具备完整管理权）。

### 4. 严密的全站 CSRF 防护
- 所有能够改变数据状态的 HTTP 动词请求（POST、PUT、PATCH、DELETE）强制要求携带自定义标头 `X-Requested-With: Mailhearth`。根据浏览器同源安全策略，未经跨域资源共享（CORS）显式放行的第三方恶意站点无法伪造该自定义标头。
- 请求包含 `Origin` 标头时，系统会严格校验其与请求的主机名一致（请求来自受信代理时，以 `X-Forwarded-Host` 为准）。

### 5. 不可信邮件正文的深度沙箱防御（Untrusted Content Sandboxing）
邮件是外部不可信内容的最常见来源，Mailhearth 实施了业内最严格的多阶段安全清洗流水线：
- **服务端深度白名单消毒**：邮件 HTML 首先经过 `bluemonday` 严格标签白名单过滤，紧接着执行第二道 DOM 遍历：彻底剥离高危 CSS 伪协议（如 `expression`、`url()`、`position: fixed` 等覆盖钓鱼样式），将 `cid:` 内联图片重写为受权限保护的安全分段端点，强制将所有外链附加 `target="_blank" rel="noopener noreferrer"`。
- **默认拦截外部追踪图片**：所有外部引用的远程图片默认阻断加载，彻底瓦解邮件营销像素与发件人追踪；仅在用户明确点击「加载图片」时按需请求。
- **无脚本沙箱独立渲染**：消毒后的邮件正文通过独立的受保护 URL 输出，强制响应头：
  ```http
  Content-Security-Policy: default-src 'none'; img-src 'self' data:; style-src 'unsafe-inline'; script-src 'none'; form-action 'none'
  ```
  并在前端 `<iframe sandbox="allow-same-origin allow-popups ...">` 中呈现，**绝对不包含 `allow-scripts`**。这意味着即便黑客构造了极其罕见的未披露 XSS 载荷，在无脚本沙箱与极端 CSP 的双重封锁下，浏览器内核也绝对无法执行任何脚本代码。
- **无 Cookie 的短效 HMAC 视图令牌**：iframe 的内容加载通过短期有效、绑定具体成员、邮箱、文件夹及邮件 UID 的 HMAC view token 进行认证，URL 请求本身不依赖 Cookie，彻底防止越权浏览。
- **附件安全投递**：所有文件附件强制附带 `Content-Disposition: attachment` 与 `X-Content-Type-Options: nosniff` 标头，除明确安全的位图、纯文本或 PDF 外，HTML、SVG、XML 格式文件坚决禁止内联执行。
- **邮件撰写与签名对称消毒**：用户在富文本编辑器中撰写的正文与签名在发往 SMTP 前，同样经过相同的服务端消毒清洗，防止因本地插件篡改而在发信时污染外部收件人。

### 6. 应用安全标头基线
- 拦截点击劫持：全站默认下发 `X-Frame-Options: DENY`；
- 隐私外泄保护：强制下发 `Referrer-Policy: no-referrer`；
- 前端单页应用专属 CSP：主页面严格限定 `script-src 'self'`；
- 敏感接口缓存防护：所有 `/api/` 接口强制响应 `Cache-Control: no-store`。

### 7. 协议连接与证书安全
- 每一个启用的 IMAP、SMTP 及 ManageSieve 协议连接必须严格校验远程服务器证书与主机名（SNI），默认依托宿主机受信根证书库，同时支持管理员挂载企业专用私有 CA 证书包。
- 系统**坚决不提供**任何「忽略证书错误」或「跳过 TLS 校验」的不安全后门选项。

### 8. 全流程审计轨迹（Audit Trail）
- 每一个涉及组织架构变动、成员状态流转、服务商连接变更、凭据轮换与权限调整的操作，均强制记录操作者 ID、客户端 IP、操作时间、目标对象及变更详情快照至不可篡改的 `audit_log` 审计表中。

## 生产部署安全建议

1. **强制 HTTPS 并妥善配置反向代理**：务必在前端反向代理（Caddy、Nginx）上配置完备的 TLS 证书终结，并将 `MAILHEARTH_BASE_URL` 设为 `https://...` 协议地址（会话 Cookie 默认附加 `Secure`，除非显式关闭，否则 `http://` 基础地址会导致启动失败）；仅在反向代理受信且正确注入标头时开启 `MAILHEARTH_TRUST_PROXY=true`。
2. **主加密密钥（master.key）隔离保存**：切勿将 `/data/master.key` 与常规业务数据库混合备份在同一个公网对象存储中。建议将 `master.key` 作为机密文本单独保存在团队的企业级密码管理器（如 1Password、Bitwarden）或硬件加密安全模块中。
3. **分配专用服务商 API Token**：在 Purelymail 或 Migadu 管理后台创建 API 凭据时，请专卡专用，切勿与其他业务系统共用同一个令牌，以便在出现异常时能独立吊销而互不影响。
4. **服务商母账号启用两步验证 (2FA)**：务必在邮件服务商的官方网页控制台中为团队管理账户开启多因素认证（2FA/TOTP），为基础设施提供最高级别的底座保障。
